\title{A Bounded Protocol Audit of Parsl with TLA+:\\
\large Ownership, Retry, and Message Correlation in Distributed Workflows}
\author{TLA+ Parsl Audit Project}
\date{October 2026}

\begin{document}
\maketitle

\begin{abstract}
Workflow APIs make a distributed execution graph look like a local Python program, but correctness
depends on ownership transfers between futures, executors, workers, providers, transports, and
staging services. This paper presents a small executable TLA+ abstraction of Parsl designed for a
bounded protocol audit rather than a complete implementation model. The abstraction separates a
logical task from its physical execution attempts, transport messages, result generations, and
monitoring state. We use a source--model--runtime evidence chain: a source transition is encoded
in a \emph{Current} model, explored with TLC, exercised where possible by a focused Parsl runtime
probe, and compared with a candidate \emph{Fixed} protocol. The communication-first audit covers
dependency blocking, futures, retry, worker and provider failure, timeout and stale results,
provisioning, scaling, memoization, and data readiness. The repository contains 676 TLA+ modules,
1,478 TLC configurations, 486 foundational runtime entries, and a 318-record risk ledger. The
central result is a reusable safety vocabulary: failed communication must preserve ownership or
make failure explicit; results must carry attempt identity; and terminal state must be monotone.
The ledger records source-backed protocol risks, not claims that every entry is a confirmed upstream
defect. The paper reports three detailed counterexample patterns and gives commands for reproducing
the bounded verification and runtime checks.
\end{abstract}

\noindent\textbf{Keywords:} Parsl, TLA+, TLC, workflow systems, futures, asynchronous messaging,
retry, formal methods

\section{Introduction}
Parsl is a Python workflow system in which an application builds a dataflow graph and a dataflow
kernel (DFK) arranges execution on local or remote resources. The user sees apps and futures; the
implementation crosses several asynchronous boundaries. A task can be accepted by the DFK, queued
by an executor, serialized into a message, launched by a worker, reported to a result collector, and
finally resolved as a future. Providers and staging components introduce additional boundaries for
resources and files. Each boundary can fail independently of the user function. This architecture
places Parsl in the broader family of dataflow and scientific workflow systems such as Pegasus,
Swift, Dask, and Ray \cite{babuji2019parsl,deelman2015pegasus,wilde2011swift,rocklin2015dask,moritz2018ray}.

This creates a characteristic verification problem. A call stack is a poor description of the
system's safety properties: a task may be removed from one queue before it is accepted by the next
component, and a delayed result may arrive after a retry has become current. The useful question is
instead \emph{who owns the task now, which attempt generated this message, and has terminal state
already been published?} We therefore model the following identity chain:

\begin{figure}[h]
\centering
\fbox{\parbox{0.86\textwidth}{\centering
logical task -- physical attempt -- transport message -- Future and monitoring record}}
\caption{Ownership and identity flow used by the abstraction.}
\label{fig:ownership}
\end{figure}

The motivating example is a task-dispatch send failure in the HTEX path. A source-like sequence
dequeues a pending task and then calls a socket send. If the send raises, the task is no longer in
the pending queue, is not owned by a manager, and has not been terminalized. A Future can remain
pending indefinitely. This is a small state machine, but it is difficult to see in a conventional
unit test because it requires a particular interleaving at a process boundary.

The audit asks three questions:
\begin{enumerate}
  \item How can ownership be preserved when a communication operation fails between two Parsl
        components?
  \item How should retry results be correlated with the current physical attempt so that late
        results cannot overwrite a newer outcome?
  \item Which asynchronous races change an observable terminal state, and which can be safely
        isolated as stale, malformed, or duplicate input?
\end{enumerate}

The contributions are fourfold. First, we give a compact executable abstraction that keeps logical
tasks separate from attempts, messages, and futures. Second, we define a protocol-oriented set of
safety properties covering dependencies, ownership, retries, terminality, and stale messages.
Third, we connect bounded TLC exploration to deterministic Python probes and a source-indexed ledger.
Finally, we show representative communication and asynchronous counterexample patterns and state
the limits of what they establish.

The rest of the paper is organized as follows. Section~2 describes Parsl's failure surface.
Section~3 explains the audit method and evidence discipline. Section~4 presents the TLA+ state
machine and invariants. Section~5 maps the abstraction to source paths and runtime probes.
Section~6 gives three case studies. Section~7 evaluates the artifact and regression suites.
Sections~8 and~9 discuss implications and threats to validity, and Section~10 gives reproduction
commands and the conclusion.

\section{Parsl Background and Failure Surface}
\subsection{Logical workflow and physical execution}
An app invocation creates a logical task with dependencies on input futures. The DFK does not
execute the Python body directly in the caller's thread: it schedules work through an executor,
which may use a manager and remote workers. A provider requests and releases resources from a batch
scheduler or cloud service. DataFuture and staging machinery may make a file available only after a
transfer has completed. Monitoring and persistence record progress independently of the application's
future callbacks.

For verification we use five identities:
\begin{description}
  \item[Logical task] the stable user-visible unit and its dependency set.
  \item[Physical attempt] one execution generation of that task; retries create a new generation.
  \item[Message] a serialized command, result, acknowledgement, heartbeat, or provider event.
  \item[Future] the completion object exposed to the caller; it must resolve at most once.
  \item[Monitoring record] an operational view of state, useful for diagnosis but not a replacement
        for task ownership.
\end{description}

The important distinction is between a failed operation and an explicit terminal failure. A send
exception is not itself a task result. If the implementation removes the only owner and then lets
the exception escape, the logical task is lost. Conversely, a delayed result after a timeout is not
necessarily a new result for the logical task: it may belong to an obsolete attempt.

\section{Audit Methodology}
\subsection{Source-to-model-to-runtime workflow}
The audit uses a four-stage discipline. We first identify a source transition and its ownership
boundary. We then encode a minimal source-like transition in a \emph{Current} TLA+ module. The
Current specification is expected to violate a named invariant for the selected failure. A
\emph{Fixed} module adds the smallest protocol change that should preserve the invariant: retain a
queue owner until acknowledgement, tag results with an attempt generation, isolate malformed input,
or snapshot a collection before callback fan-out. Finally, a Python probe exercises the real Parsl
path or a deterministic test double when the real boundary is difficult to control. This separation
between model checking and proof-oriented validation follows established industrial TLA+ practice
\cite{newcombe2015formal,cousineau2012tlaps,chaudhuri2010tlaps}.

\begin{figure}[h]
\centering
\fbox{\parbox{0.88\textwidth}{\centering
source transition -- Current TLC trace -- runtime probe -- Fixed invariant -- ledger record}}
\caption{Evidence ladder connecting source review, model checking, and runtime observation.}
\label{fig:evidence}
\end{figure}

This evidence chain prevents a model-only observation from being presented as a production defect.
The ledger stores the source location, model and configuration, expected result, probe type,
candidate protocol, and limitations. A record is a source-backed protocol risk unless the project
has independently confirmed it in an upstream release.

\subsection{Finite scope and stopping rule}
The project deliberately does not simulate all Python objects or every backend detail in the Parsl
paper. Constants bound tasks, attempts, workers, messages, and queue lengths. The selected scope
stops when each chosen communication path has (i) a source note, (ii) a Current and Fixed model or
an explicit reason why one is not meaningful, (iii) a runtime probe where feasible, and (iv) a
reproducible ledger entry. Expanding to another provider is a scope change, not an implicit promise
of exhaustive coverage.

TLC configuration suites are split into foundational Fixed cases and focused Current cases. The
foundational suite is a regression gate: all cases should pass. Current cases are negative tests:
they should produce the documented counterexample. Simulation bounds explore interleavings and are
not an unbounded proof \cite{yu1999modelchecking,konnov2019symbolic}. Runtime probes complement rather than replace TLC: probes exercise Python
and socket behavior, while TLC explores combinations that are hard to schedule reliably.

\section{TLA+ Abstraction}
\subsection{State variables}
The core model uses finite sets of tasks, attempts, and message identifiers. The key state variables
are shown below; extended modules refine them for providers, staging, monitoring, and cancellation.

\begin{table}[h]
\centering
\caption{Core state variables and their interpretation.}
\label{tab:variables}
\normalsize
\begin{tabularx}{\textwidth}{>{\ttfamily\raggedright\arraybackslash}p{0.25\textwidth} X}
\toprule
Variable & Meaning \\
\midrule
taskState[t] & logical task state: blocked, ready, queued, running, succeeded, failed, or cancelled \\
attempt[t] & current physical-attempt generation for logical task t \\
owner[t] & component that currently owns delivery or execution responsibility \\
msgState[m] & created, sent, delivered, rejected, duplicate, stale, or dropped \\
msgAttempt[m] & attempt generation carried by result/command message m \\
futureState[t] & unresolved, resolved-success, resolved-failure, or cancelled \\
retryCount[t] & number of retries consumed by logical task t \\
monitorState[t] & last operational observation; it cannot reopen a terminal Future \\
\bottomrule
\end{tabularx}
\end{table}

Dependencies are represented by a finite relation \texttt{deps} between finite task sets. A task may
enter \texttt{ready} only when all dependencies have succeeded and their result values are
available. Memoization adds a cache keyed by an input identity; a cache hit produces a result
without creating a new physical attempt, but still resolves the logical Future exactly once.

\subsection{Actions}
The following pseudocode is a compressed version of the executable modules. It omits set-builder
syntax that is not needed to understand the protocol boundary.

\begin{lstlisting}[language={},caption={Core Current/Fixed protocol actions.}]
Dispatch(t) ==
  taskState[t] = "queued" /\
  LET m == NewCommand(t, attempt[t]) IN
    IF SendSucceeds(m)
    THEN owner[t] := "manager" /\ msgState[m] := "sent"
    ELSE Current: owner[t] := "none" /\ msgState[m] := "dropped"
         Fixed:  owner[t] := "executor" /\ taskState[t] := "queued"

Timeout(t) ==
  taskState[t] = "running" /\ retryCount[t] < RetryLimit /\
  attempt[t] := attempt[t] + 1 /\ taskState[t] := "queued"

DeliverResult(m) ==
  IF msgAttempt[m] = attempt[msgTask[m]]
  THEN resolve Future and publish terminal monitoring state
  ELSE msgState[m] := "stale" /\ no logical state changes
\end{lstlisting}

The model treats a message as a protocol object, not merely as a value. A multipart message can
fail at framing or decoding before a task is touched. A duplicate message is consumed idempotently;
a stale message is rejected using the current attempt generation. The same rule applies to worker
results, manager-loss synthetic results, and late staging notifications. These assumptions are
consistent with the atomic multipart and peer-ordering guarantees specified by ZMTP, but the
application-level retry and ownership policy remains outside the transport
\cite{zmtp37,zeromqguide,birman1987reliable}.

\subsection{Safety properties}
Table~\ref{tab:invariants} lists the invariants used in the foundational suites. They are safety
properties: a finite counterexample is sufficient to disprove one, while a passing bounded run only
supports the stated finite instance.

\begin{table}[h]
\centering
\caption{Main invariants and the failure they exclude.}
\label{tab:invariants}
\normalsize
\begin{tabularx}{\textwidth}{>{\raggedright\arraybackslash}p{0.25\textwidth} X}
\toprule
Invariant & Intended guarantee \\
\midrule
DependencySafety & a task cannot execute or publish success before all dependencies succeed \\
OwnershipSafety & every non-terminal task is queued, assigned, or explicitly owned by a retry/failure path \\
RetryBound & retries never exceed the configured limit and each retry advances the generation \\
ResultConsistency & only a result from the current attempt can resolve the logical Future \\
TerminalStability & success, failure, and cancellation are monotone and cannot be reopened \\
StaleIsolation & stale, duplicate, and malformed messages do not mutate current logical state \\
MemoizationSafety & a cache hit is equivalent to one successful result, not a second completion \\
ReadinessSafety & a task consuming staged data observes only atomically published data \\
\bottomrule
\end{tabularx}
\end{table}

These properties intentionally cross component boundaries. For example, ResultConsistency is not
an executor-only property: it constrains the relation between worker output, serialization metadata,
the result collector, and the Future callback.

\section{Source and Runtime Evidence}
\subsection{Mapping to Parsl components}
The repository maps DFK/Future paths to logical state and terminality; HTEX interchange, manager,
worker, and message-manager paths to frames, ownership, and ACKs; provider adapters to request,
running, cancellation, and scale; and DataManager/file-transfer paths to publication and readiness.
The model follows stable interfaces (enqueue, send, launch, retry, publish, observe) rather than
copying every backend call frame. The staging and provenance vocabulary is compatible with the
workflow provenance literature and W3C PROV data model \cite{moreau2013prov,cuevas2013workflows,chen2021provenance}.

\subsection{Probe design}
Probes are small Python programs under the runtime probe tree. They use deterministic doubles for
socket send failures, malformed frames, provider responses, callback mutation, and file publication.
Where practical, a probe enters a real in-process Parsl path and replaces only the failure boundary.
This is particularly useful for confirming that a source-level exception is reachable without
requiring a cluster. Probe results are classified as observed, expected, or blocked; a blocked probe
is never silently converted into a model claim.

One representative probe constructs a fake transport whose first send raises and whose second send
succeeds. Similar doubles inject a delayed result, malformed command, or ACK failure. Each probe is
small enough to map to one action and invariant.

To make this claim auditable, the repository includes a machine-readable source-to-model manifest
(\texttt{docs/source-model-evidence.json}) and a validator
(\texttt{scripts/verify\_source\_coverage.py}). The
manifest records nine representative boundaries, their inspected Parsl source paths, model files,
runtime probes, and safety properties. The validator checks that every declared model and probe is
present and reports the current inventory (676 TLA+ modules and 490 runtime probe files). This is
traceability evidence, not line coverage: it demonstrates that the central protocol paths have
linked artifacts while leaving backend-specific depth and external source revision explicit.

\section{Findings and Case Studies}
\subsection{Case 1: HTEX dispatch send failure (BUG-335)}
\paragraph{Source transition.} A pending task is selected and removed from the queue before the
interchange sends a command to a manager. The send operation can raise due to a closed or broken
ZeroMQ socket. The exception path does not itself create a task result.

\paragraph{Current trace.} Table~\ref{tab:bug335} gives the minimal four-state trace. The failure
is not a worker failure: the task never reached a worker, so retry logic attached to execution does
not necessarily run.

\begin{table}[h]
\centering
\caption{Representative Current counterexample for BUG-335.}
\label{tab:bug335}
\normalsize
\begin{tabularx}{\textwidth}{c p{0.23\textwidth} p{0.23\textwidth} p{0.30\textwidth}}
\toprule
State & Queue & Owner & Observation \\
\midrule
0 & task t pending & executor & Future unresolved \\
1 & empty & executor & dequeue completed \\
2 & empty & none & socket send raises \\
3 & empty & none & no result, retry, or terminal failure \\
\bottomrule
\end{tabularx}
\end{table}

\paragraph{Violated property.} OwnershipSafety fails because a non-terminal task has no owner.
DependencySafety and RetryBound are irrelevant until ownership is recovered; this explains why a
test that only checks eventual worker retry can miss the case.

\paragraph{Runtime evidence and candidate fix.} The deterministic send-failure probe reaches the
same transition shape. The candidate protocol retains executor ownership until the send is
acknowledged, or converts the transport exception into an explicit terminal transport failure. A
bounded Fixed model passes OwnershipSafety and TerminalStability for the selected constants. The
ledger records this as a source-backed risk, not as evidence that every Parsl deployment loses
tasks.

\subsection{Case 2: retry and stale result correlation}
\paragraph{Scenario.} Attempt 0 starts, times out, and causes attempt 1 to become current. Attempt
1 succeeds. A delayed result from attempt 0 then arrives through the result collector. If the
collector keys only on the logical task identifier, the late result can overwrite the successful
value or invoke a second completion callback.

\begin{figure}[h]
\centering
\fbox{\parbox{0.9\textwidth}{\centering
attempt 0: running -- timeout -- attempt 1: running -- success;\\[2pt]
late attempt-0 result -- reject as stale, consume idempotently, no state change}}
\caption{Retry timeline and stale-result rejection.}
\label{fig:retry}
\end{figure}

\paragraph{Model result.} The model carries the attempt generation in every command and result
message. DeliverResult compares the message generation with the current generation. Equality
resolves the Future once; a smaller generation changes only the message state to \texttt{stale}.
The Fixed model therefore satisfies ResultConsistency, TerminalStability, and StaleIsolation.
The scenario also exposes why a retry counter alone is insufficient: the counter bounds the number
of attempts but does not identify which result is current. This is the same distinction made by
logical clocks and consistent distributed observations
\cite{lamport1978time,chandy1985snapshot,herlihy1990linearizability}.

\paragraph{Implementation implication.} Correlation metadata must survive serialization and route
changes. It is not enough to add a generation field to an executor-local object if the field is
dropped when a result is framed, decoded, or converted into a synthetic manager-loss result.

\subsection{Case 3: callback mutation during failure fan-out}
\paragraph{Scenario.} A failure path iterates a live task dictionary and synchronously invokes
Future callbacks. A callback removes an entry, adds a replacement, or triggers cancellation while
the iteration is in progress. The container mutation can raise an exception and leave unrelated
Futures unresolved.

\paragraph{Model and fix.} The model represents the registry as a finite set and the callback as an
action that can mutate it. The Current action permits iteration and mutation in one transition and
can leave a pending Future without a terminal event. The candidate Fixed protocol snapshots the
entries before callback invocation, then records each terminal transition independently. This is an
asynchronous terminality risk rather than a transport framing risk, but it uses the same principle:
the operation that loses control must retain explicit ownership until terminal state is published.

The same vocabulary also produced focused refinements for malformed command ingress (BUG-336),
command-reply send failure (BUG-337), heartbeat ACK send failure (BUG-338), and a manager-loss
synthetic result that fails during transport (BUG-004 refinement). In each case, the safe alternatives
are to preserve the old owner, install an explicit retry owner, or publish a terminal failure.

\section{Discussion}
\subsection{Ownership is a cross-component abstraction}
The recurring pattern is an ownership gap. A queue, socket, worker, provider, or staging service may
be treated as if it has accepted responsibility before it has acknowledged the transfer. The
implementation then has no place to retry from when the next operation fails. Modeling ownership
explicitly makes the gap visible without reproducing every Python call frame. This complements
lineage-based recovery in MapReduce and Spark, and ownership-based recovery in distributed futures
systems \cite{dean2004mapreduce,zaharia2012resilient,wang2021ownership}.

\subsection{Terminality is stronger than eventual observation}
Monitoring events, heartbeats, and database rows are observations. They can arrive late, be
duplicated, or disappear during shutdown. A Future's terminal state must therefore be monotone and
independent of whether a later monitoring event is processed. This separation also clarifies why a
successful retry must not be reopened by an old result or a stale failure notification.

Candidate Fixed protocols are designs, not patches. They identify where an implementation should
retain ownership, carry correlation metadata, or isolate callbacks. A maintainer would still need
to choose API compatibility, logging, shutdown, and performance behavior before applying a fix.

\section{Threats to Validity and Limitations}
\begin{table}[h]

The most important limitation is scope. This is not a full simulation of every component described in
the Parsl paper. It is a small executable model of the most error-prone interactions, with
communication and asynchronous terminality prioritized. The scope is explicit so that additional
components can be added as separate, reviewable evidence rather than silently inflating the claim.
The paper also avoids implying that coordination is free or always solvable under arbitrary failures;
classic results establish fundamental limits for consensus and consistency under faults
\cite{fischer1985impossibility,gilbert2002brewer}.

\section{Reproducibility and Conclusion}
The repository contains the TLA+ modules, TLC configurations, runtime probes, source inventory,
coverage matrix, bug ledger, Markdown report, and this compiled PDF. From a clean checkout, the
foundational commands are:

\begin{lstlisting}[language=bash]
PYTHONPATH=/tmp/parsl-source \\
  PYTHON_BIN=/tmp/parsl-venv/bin/python \\
  PARSL_SOURCE=/tmp/parsl-source \\
  bash scripts/runtime_foundational_smoke.sh

JAVA_BIN=/path/to/java \\
  TLA_JAR=/path/to/tla2tools.jar \\
  TLC_SIMULATE=100 \\
  bash scripts/tlc_foundational_smoke.sh
\end{lstlisting}

The exact paths can be changed for a local installation; the scripts report missing tools rather
than silently skipping a suite. Focused Current runners are useful when reviewing a case study,
while the foundational scripts are the release-style regression gate. The interactive companion
under \texttt{site/dist} provides a presentation view, but the paper does not depend on JavaScript.

This bounded audit shows why a small model can be useful even for a large workflow system. Parsl's
surface area is broad, but the safety vocabulary is compact: preserve ownership across failed
communication, correlate every result with its physical attempt, isolate malformed or stale input,
and make terminal state monotone. TLC supplies interleaving counterexamples; runtime probes connect
those traces to executable boundaries; and the ledger preserves the distinction between a plausible
risk and a confirmed defect. These principles are the practical outcome of the project and the
starting point for deeper audits of specific backends.

\subsection{How to audit one row}
For each row, a reviewer can follow the same five-step trail:
\begin{enumerate}
  \item open the source path and identify the ownership-changing operation;
  \item open the named TLA+ module and locate the corresponding action and Current/Fixed split;
  \item open the runtime probe and identify the injected failure or adversarial input;
  \item run the relevant TLC configuration and inspect the invariant or counterexample trace;
  \item compare the result with the ledger entry, including its limitation and confidence label.
\end{enumerate}

The machine-readable version of this catalog is \texttt{docs/source-model-evidence.json};
\texttt{scripts/verify\_source\_coverage.py} checks that every declared model and probe exists. A
passing check establishes repository traceability. It does not establish that every function in the
external Parsl source tree has been modeled.

The normalization is what makes cross-component comparison possible. A provider poll and a ZMQ
receive are not implemented the same way, but both can be checked for late input, ownership loss,

is intentionally weak: queue bounds, symbolic bytes, deterministic scheduler responses, and the
absence of arbitrary Python heap mutation.
